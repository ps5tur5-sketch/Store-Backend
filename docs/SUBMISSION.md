## 2. Частичный сбой и недобросовестный поставщик

```bash
docker compose exec backend node dist/scripts/scenario-stage2.js
```

Сценарий создаёт отдельных продавцов: обычная выдача Steam за 500; GTA V за 1490 с `error_after_issue`; отсутствие Discord за 399. Поставщик GTA фиксирует выдачу, но отвечает ошибкой. Система сама проверяет реестр, выдаёт единственный правильный ключ и сохраняет доказательство. Discord отменяется с возвратом. Повтор оплаты и recovery не меняют итог.

Ожидается `partially_refunded`, `paid=2389`, `delivered=1990`, `refunded=399`, `pending=0`, `balanced=true`, `repeat_preserves_money=true`. [Сохранённый вывод](verification/stage2-scenario.txt). Идентификаторы и время при новом запуске отличаются.

Полная проверка на отдельной PostgreSQL:

```bash
docker compose --profile test run --rm --build tests
```

В 71 интеграционном тесте отдельно проверяются `duplicate_code`, `wrong_code`, `error_after_issue`, `timeout_after_issue`, ошибочная сумма оплаты, конкурентные повторы, настоящий SIGKILL между внешней выдачей и локальной фиксацией, просроченная аренда worker, лимиты, история на дату, права доступа, возвраты и цены ключей. Это не очищает рабочий volume. [Матрица проверок](VERIFICATION.md).

## 3. Проверка денег

```bash
docker compose exec backend node dist/scripts/reconcile.js
```

У каждой завершённой оплаченной позиции: `paid = delivered + refunded`, `pending=0`, `settled=true`. Пока выдача идёт: `paid = delivered + refunded + pending`.

В сводке ожидаются пустые `ledger_imbalances`, `invalid_deliveries`, `delivered_not_paid`, а также `wallet.balanced=true` и `withdrawals.balanced=true`. `paid_not_delivered` может содержать оплаченные задания во время работы; после завершения сценария их не остаётся. Денежные проводки в каждой валюте суммируются в ноль; комиссия демо равна нулю.

История позиции/группы: `GET /api/orders/:id/history?at=<ISO8601>`. Денежный отчёт администратора: `GET /api/admin/money?from=<ISO8601>&to=<ISO8601>`, период `[from,to)`. Приватные запросы требуют bearer-токен собственного аккаунта или администратора; скрипт сверки авторизуется демо-администратором автоматически. [Пример сверки](verification/runtime-verification.json), [объяснение COMMIT и ограничений старых данных](ARCHITECTURE.md).

## 4. Фактически затраченное время

По зафиксированным этапам сессии до подготовки публикации: около **3 часов 58 минут**. Первый блок — около 1 ч 50 мин; платежи, история, единый аккаунт, выводы и финансы — 1 ч 17 мин; партии и резервирование — 33 мин; индивидуальные цены и проверка кабинета — 18 мин. Это время работы с coding-agent, не заявление о самостоятельных человеко-часах кандидата. Подготовка документов, коммитов и GitHub-публикации учитывается отдельно в результатах передачи.

## 5. Изменение кода на звонке

**Готовность и формат согласую отдельно.** Для разбора доступны воспроизводимые сценарии и отдельная тестовая БД; например, можно изменить правило лимита поставщика либо политику отображения репутации и показать соответствующую проверку.

## Соответствие задачам

| Задача PDF | Результат |
| --- | --- |
| 1. Несколько товаров, частичный сбой, деньги, повторы, перезапуск | Группа позиций, отдельная выдача/возврат, двойная запись, идемпотентность, очередь/recovery |
| 2. Дубли, чужие коды, ошибка после выдачи, авторазбор | Проверяемый реестр, уникальные факты, стабильный request_id, resolve/отмена, доказательства |
| 3. Всплеск и лимит — бонус | Общий устойчивый бюджет за 60 секунд, оплаченная очередь, отложенные попытки, прогресс |
| 4. История на дату — бонус | Добавляемые факты и проводки, границы COMMIT новых операций, периодический отчёт и сверка |

Неопределённый результат внешней системы ожидает доступности авторитетного resolve. Точный COMMIT не восстанавливается задним числом для данных, которые существовали до его регистрации: они отмечены `legacy_reconstructed`. Эти ограничения явно описаны, а не скрыты за заявлением о безусловной гарантии.
